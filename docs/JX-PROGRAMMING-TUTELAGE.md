# JX Programming Tutelage

## The complete working guide to canonical JX, its PHP-backed front end, PASL lowering, Bags, Books, JXL, and native execution

**JX** — pronounced *jinx* — is a readable, PHP-backed programming language/compiler/runtime system built around a simple idea:

> **Let programmers describe meaning clearly. Let the compiler remember the expensive decisions. Let prepared code repeat the cheap part.**

This guide is deliberately broad. It is intended to become the main programming tutelage for people, AI systems, compiler authors, runtime authors, and host implementers working with JX.

JX is still evolving. For that reason every feature in this guide belongs to one of four status classes.

| Status | Meaning |
|---|---|
| **ACTIVE** | Accepted or directly exercised by the current JX/PASL implementation and regression gates. |
| **PHP-BACKED** | Available through the JX PHP host/runtime API even when no standalone canonical `.jx` parser form exists yet. |
| **JXL** | Prepared executable representation generated by the compiler. It is not normal hand-written source. |
| **PLANNED** | A deliberate language direction or semantic slot that is not claimed as active syntax yet. |

When examples are marked **PLANNED**, treat them as design guidance, not as a promise that `jx-run.php` accepts them today.

---

# Part I — The mental model

## 1. JX in one picture

```text
human / AI
   |
   | canonical readable .jx
   v
PHP-backed JX front end
   |
   | parse / validate / canonicalize / resolve
   v
semantic JX + PASL lowering
   |
   +-------------------+--------------------+
   |                   |                    |
   v                   v                    v
web/PHP host         JXL prepared         target-native
runtime              executable           ELF / PE / other
   |                   |                    |
   +-------------------+--------------------+
                       |
                       v
                  .64B Book
                       |
                       v
              JX / WSJX64 / OSAura64
```

The architecture separates **authoring** from **repetition**.

Canonical JX is allowed to contain useful names, aliases, types, Bags, Pages, Controls, and explanatory structure. The compiler and admission layer may perform comparatively expensive work once. The runtime should not repeatedly parse names or rediscover facts that were already known.

The project shorthand is:

> **Resolve cold -> bind once -> execute hot.**

And for state:

> **Bags remember. Registers react. Prepared code executes.**

---

## 2. JX is PHP-backed, not PHP trapped

JX uses PHP heavily today because PHP is excellent at the jobs a language front end needs:

- text processing,
- parsing orchestration,
- compiler tooling,
- server/web hosting,
- filesystem/package work,
- JSON/data manipulation,
- extension/plugin integration,
- rapid diagnostics,
- deterministic compiler scripting.

That does **not** mean native JX must execute PHP source.

The native direction is:

```text
canonical JX
 -> PHP-backed compiler/front end
 -> semantic lowering
 -> JXL and/or native code
 -> .64B compiled Book
 -> native runtime
```

A browser/web deployment may intentionally keep PHP as the host. A native `.64B` deployment should not require PHP source merely to wake and execute the Book.

# Part II — Source form and lexical rules

## 3. Files

### ACTIVE

Canonical JX source normally uses:

```text
.jx
```

PASL source normally uses:

```text
.pasl
```

Compiled PASL bytecode currently uses:

```text
.pbc
```

Native compiled Books use:

```text
.64B
```

Prepared JXL sections may use:

```text
.8B
.jxl
```

as standalone/debug representations, but JXL is naturally embedded in `.64B` Books.

---

## 4. Statements and semicolons

### ACTIVE

The current JX/PASL surface is semicolon-oriented:

```jx
$x = 10;
$y = 20;
$sum = $x + $y;
```

The `$` prefix is accepted in PASL-style variables. Several JX object examples also accept unprefixed names:

```jx
bag = Bag.underwrite(256);
ref = bag.sign("msg");
bag.set("hello").commit(ref);
```

For teaching and portability, use `$` for arithmetic/PASL variables and clear unprefixed identifiers for JX objects only when following an established example. Future canonicalization may normalize both.

---

## 5. Comments

### ACTIVE

The active front ends strip the familiar forms:

```jx
// line comment
# line comment

/*
   block comment
*/
```

Example:

```jx
$sum = 0;             // accumulated total
# another comment
$sum += 10;
```

Do not put meaningful syntax inside comments and expect it to affect preparation; comments are source-only information.

---

## 6. Identifiers

### ACTIVE

PASL variables use ordinary identifier shapes:

```text
[A-Za-z_][A-Za-z0-9_]*
```

Examples:

```jx
$count = 1;
$_scratch = 0;
$playerHealth = 100;
```

The current PASL compiler normalizes variable identity to lowercase internally. Do not depend on case differences to create two distinct arithmetic variables.

Prefer:

```jx
$total = 0;
$Total = 0;   // avoid this as a second identity
```

---

## 7. Canonical aliases

### ACTIVE / PHP-BACKED

JX supports aliases as a compiler convenience, not as runtime ambiguity.

For example:

```text
enqueue
append
push
```

may canonicalize to one operation such as:

```text
BPUSH
```

Other examples documented by the repository include:

```text
Book.load       -> Book.open
Bag.allocate    -> Bag.underwrite
deliver(...)    -> delivery(...)
JNE             -> PASM JNZ
```

The important rule is:

> **Aliases disappear before hot execution.**

Diagnostics may remember the source spelling for provenance, but the executable path sees the canonical identity.

# Part III — Values and types

## 8. Integer

### ACTIVE

Integer arithmetic is the strongest directly compiled scalar path today.

```jx
$x = 10;
$y = -3;
$z = $x + $y;
```

The active PASL compiler maps integer working variables into its register set.

### Operators actively lowered

```text
+   addition
-   subtraction
*   multiplication
/   integer division path
%   modulo
&   bitwise AND
|   bitwise OR
^   bitwise XOR
<<  shift left
>>  shift right
```

Comparison conditions actively understood include:

```text
==
!=
<
<=
>
>=
```

---

## 9. Float

### ACTIVE at JX value boundary / PHP-BACKED more broadly

The JX value evaluator recognizes decimal numeric literals such as:

```jx
$x = 3.5;
$rate = -0.25;
```

The current hot PASL register compiler is principally integer/complex oriented. Do not assume every floating-point expression has the same native lowering maturity as integer algebra yet.

Use floats through the PHP-backed runtime where needed and treat deeper typed native float lowering as an evolving compiler area.

---

## 10. Boolean

### ACTIVE as JX values / PHP-BACKED

Boolean is part of JX's binding coercion vocabulary and runtime data model.

Conceptually:

```text
true
false
```

JX's native design prefers bit packing for large boolean state:

```c
uint64_t boolreg[4];  // 256 booleans = 32 bytes
```

The design law is:

> **Bits for truth, native words for numbers, Bags for structure.**

Not every boolean surface spelling is yet a dedicated PASL scalar opcode; numeric conditions (`0` false-like, nonzero true-like) are currently central to compiled branch lowering.

---

## 11. String

### ACTIVE at JX runtime boundary

The JX front end recognizes quoted string values:

```jx
$name = "JX";
$message = 'hello';
```

Strings are especially common in:

- Bag nodes,
- Book names,
- Delivery paths,
- Control labels,
- styles,
- SQL/NoSQL descriptors,
- source binding descriptors,
- diagnostics.

A string used as semantic state normally belongs in a Bag when it must persist or be shared.

---

## 12. Complex

### ACTIVE

Complex numbers are first-class in the PASL/JX stack.

Declaration:

```jx
complex $z = 3+4i;
complex $w = 1-2i;
complex $p;
```

Assignment/arithmetic:

```jx
$p = $z * $w;
```

Complex values use a real/imaginary pair. In the current PASL register compiler a complex variable consumes two working registers.

Accepted literal shapes include forms such as:

```text
3+4i
1-2i
i
-i
7
```

The runtime can also parse JX complex literals during binding coercion.

---

## 13. Decimal

### PHP-BACKED plugin

Fixed-scale decimal arithmetic is supplied through the decimals plugin/JX Decimal facilities.

Use Decimal where binary floating-point is not the desired semantic model—for example money-like or exact fixed-scale calculations.

Do not treat Decimal as identical to native float. It is a semantic numeric type with its own implementation and lowering possibilities.

---

## 14. Const / immutable value

### ACTIVE JX surface

The JX engine recognizes:

```jx
const $limit = 100;
```

The value is wrapped as JX immutable state. Reading yields the contained value.

The compiler/runtime should eventually propagate const information aggressively into preparation and JXL.

Rule:

> **A const is a semantic promise first and an optimization opportunity second.**

---

## 15. Null / absence

### PHP-BACKED / runtime semantic

JX host APIs can represent absent/default values through PHP `null` and explicit defaults.

Delivery, Bag reads, bindings, data-source adapters, and host APIs should distinguish:

```text
missing
null-like value
empty string
zero
false
```

Do not collapse these merely because the PHP host can coerce them.

---

## 16. JSON-shaped data

### PHP-BACKED / binding coercion ACTIVE

Binding coercion includes `json` as a declared shape.

JSON is an interchange/data shape, not the JX memory system. Once imported into JX state, ownership belongs to Bags and the normal mutation law.

---

# Part IV — Variables and mutation

## 17. Assignment

### ACTIVE

```jx
$x = 10;
$y = $x;
$z = $x + 4;
```

JX/PASL canonicalizes mutations before target lowering.

---

## 18. Increment and decrement

### ACTIVE

All familiar forms are recognized:

```jx
$x++;
++$x;
$x--;
--$x;
```

Canonical mutation identities:

```text
VINC
VDEC
```

Where the target permits it, these may lower to one native increment/decrement operation.

---

## 19. Compound assignment

### ACTIVE

```jx
$x += 5;
$x -= 5;
$x *= 5;
$x /= 5;
$x %= 5;
$x &= $mask;
$x |= $mask;
$x ^= $mask;
$x <<= 1;
$x >>= 1;
```

Canonical operations include:

```text
VADD
VSUB
VMUL
VDIV
VMOD
VAND
VOR
VXOR
VSHL
VSHR
```

Recursive algebraic assignment remains one canonical mutation (`VALG`) even if the target needs several machine instructions.

That distinction matters: JX should not repeatedly rediscover the expression tree at runtime.

---

## 20. Algebra

### ACTIVE for integer PASL; PHP-BACKED binding algebra

Examples:

```jx
$a = 2 + 3 * 4;
$b = ($a - 5) / 3;
$c = ($b << 2) ^ 7;
```

Binding coercion has a restricted algebra evaluator for safe data shaping. It allows numbers, named/dotted fields, parentheses, unary signs, and basic arithmetic without PHP `eval()` or arbitrary function calls.

Do not confuse compiler algebra with unsafe dynamic source evaluation.

# Part V — Conditions and branches

## 21. `if`

### ACTIVE in PASL lowering

```jx
if ($x > 10) {
    $y = 1;
}
```

A non-comparison integer expression can also act as the branch condition:

```jx
if ($count) {
    $sum += $count;
}
```

The compiler compares the resulting value with zero.

---

## 22. `if / else`

### ACTIVE

```jx
if ($score >= 100) {
    $rank = 2;
} else {
    $rank = 1;
}
```

The active compiler builds explicit then/else/end labels.

---

## 23. `else if`

### Use nested `if` today

The safest active form is:

```jx
if ($x < 0) {
    $kind = -1;
} else {
    if ($x == 0) {
        $kind = 0;
    } else {
        $kind = 1;
    }
}
```

### PLANNED convenience

A canonical `elseif` / `else if` surface can lower to the same branch tree once explicitly accepted by the front end.

---

## 24. `select` / `switch`

### ACTIVE

Both `select` and `switch` are recognized by the active PASL compiler.

```jx
select ($mode) {
    case 1:
        $result = 10;
    case 2:
        $result = 20;
    default:
        $result = 0;
}
```

Equivalent accepted spelling:

```jx
switch ($mode) {
    case 1:
        $result = 10;
    default:
        $result = 0;
}
```

Current case values are integer literals.

Current lowering gives each matching case an implicit transfer to the select end after its body. Do **not** rely on C/PHP-style accidental fall-through.

This is an intentional simplification: a case is a selected block, not an invitation to continue into the next case.

---

## 25. `match`

### PLANNED canonical convenience

A value-producing `match` form is a natural future JX surface because PHP users understand it and it can lower deterministically to a select tree/table.

Proposed shape:

```jx
$result = match ($mode) {
    1 => 10,
    2 => 20,
    default => 0,
};
```

Do not claim this syntax is accepted by the active compiler yet.

---

# Part VI — Every loop family

## 26. The loop-space idea

JX/PASL treats loop bodies as compiled blocks rather than textual bodies that must be rediscovered each iteration.

Canonical loop controller concepts:

```text
LCHECK   condition
LCALL    prepared body
LCALL    prepared step (for loops when needed)
LREPEAT  loop slot
```

The current PASM target may lower `LCALL` to a direct branch because the continuation is fixed. A native target may choose a machine `call`, tail branch, or inline body.

Loop nesting is bounded. The default semantic maximum is eight nested active loop slots.

---

## 27. `while`

### ACTIVE

```jx
$counter = 5;
while ($counter) {
    $counter--;
}
```

Comparison form:

```jx
while ($i < 100) {
    $i++;
}
```

Execution model:

```text
check
 -> body block
 -> check
 -> body block
 -> ...
 -> exit
```

`continue` returns to the condition check. `break` leaves the loop.

---

## 28. `for`

### ACTIVE

```jx
$sum = 0;
for ($i = 0; $i < 10; $i++) {
    $sum += $i;
}
```

The three fields are:

```text
for (initialization; condition; step)
```

The condition may be empty for an intentionally unconditional loop:

```jx
for ($i = 0; ; $i++) {
    if ($i >= 10) {
        break;
    }
}
```

Execution model:

```text
init once
check
 -> body block
 -> step block
 -> check
```

`continue` targets the prepared step block, not the top of the body.

---

## 29. `break`

### ACTIVE inside compiled loops

```jx
while ($running) {
    if ($done) {
        break;
    }
}
```

`break` outside a loop is a compile error in the active PASL compiler.

For `switch/select`, current case lowering ends the selected case automatically; an explicit switch-break is not required for normal non-fallthrough semantics.

---

## 30. `continue`

### ACTIVE inside compiled loops

```jx
for ($i = 0; $i < 100; $i++) {
    if ($i == 50) {
        continue;
    }
    $sum += $i;
}
```

In a `for`, continue goes to the step block. In a `while`, continue goes to the condition check.

---

## 31. `do ... while`

### PLANNED surface; loop-space semantic exists

The loop-space model already reserves `DO_WHILE`, but the current PASL parser does not accept it as active syntax.

Intended form:

```jx
do {
    $attempts++;
} while ($attempts < 3);
```

Semantics:

```text
body at least once
 -> check
 -> repeat body if true
```

When implemented, `continue` should target the post-body condition check and `break` should target the loop exit.

---

## 32. `repeat`

### PLANNED surface; loop-space semantic exists

JX reserves a repeat loop as a count-oriented convenience.

Possible canonical form:

```jx
repeat (10) {
    $ticks++;
}
```

The exact active surface is not ratified yet. Compiler authors must not silently invent incompatible `repeat` syntax in one backend.

---

## 33. `foreach`

### Recognized but intentionally not active

The active PASL compiler explicitly detects `foreach` and rejects it with an explanation that collection lowering is not linked yet.

This is better than pretending the construct works.

Desired future forms should preserve collection semantics cleanly, for example:

```jx
foreach ($values as $value) {
    $sum += $value;
}
```

and possibly key/value form:

```jx
foreach ($map as $key => $value) {
    // work
}
```

JX should lower this according to the container discipline:

```text
vector -> indexed contiguous walk
queue  -> stable queue iteration contract
map    -> hash iterator
set    -> key iterator
Bag    -> canonical node iteration when explicitly requested
```

Do not force every container through one slow generic iterator when the compiler knows its discipline.

---

## 34. Infinite/service loop

### ACTIVE via ordinary conditions; use carefully

A service loop can be expressed with an unconditional `for` condition:

```jx
for ($i = 0; ; $i++) {
    // service step
    if ($stop) {
        break;
    }
}
```

For actual JX runtime services, prefer scheduler/event mechanisms rather than busy-spinning a user program. Sleeping/waking programs should not burn CPU merely to ask whether anything changed.

---

## 35. Event/reactive loop

### PHP-BACKED / runtime architecture

JX's processor-bus direction intentionally reduces polling.

The conceptual loop is:

```text
program sleeps
 -> Bag/source generation changes
 -> processor-owned bus wakes listener
 -> program checks the generation/event
 -> program reacts if needed
 -> program returns to sleep when the bus owned the wake
```

This is semantically a loop over events, but it should be implemented by scheduler wakeups rather than a user-written polling `while(true)`.

---

# Part VII — Bags: JX memory that remembers

## 36. Bag

### ACTIVE / central JX type

A Bag is mutable, underwritten JX state with identity and capacity.

First program:

```jx
bag = Bag.underwrite(256);
ref = bag.sign("msg");
bag.set("hello-jx").commit(ref);
q = bag.quotient();
```

Core idea:

```text
underwrite capacity
 -> sign intended node
 -> stage value
 -> commit using the signed reference
```

This is the memory law, not decorative ceremony.

A write should fail closed when it exceeds legal capacity or violates the handshake.

---

## 37. `Bag.underwrite(bytes)`

### ACTIVE

```jx
bag = Bag.underwrite(4096);
```

The argument is capacity/allowance for the Bag.

Alias families may canonicalize to `underwrite`, but `underwrite` is the clearest teaching form.

---

## 38. `sign(node)`

### ACTIVE

```jx
ref = bag.sign("health");
```

A signed reference authorizes the intended mutation path according to Bag law.

A reference is not a general host pointer.

---

## 39. `set(...).commit(ref)`

### ACTIVE

```jx
bag.set(100).commit(ref);
```

Verbose rhetorical form is also recognized in the language design/runtime:

```jx
bag.tell(set, 100).pass(ref);
```

Verbose forms lower toward the same canonical operation. They are not meant to create a slower second semantic system.

---

## 40. `push`

### ACTIVE JX engine method shape

```jx
bag.push("health", 100);
```

Task inherits Bag behavior in the current model, so task-like state may use Bag mutation mechanisms too.

For container disciplines, `push`, `append`, `enqueue`, and similar source spellings may canonicalize to discipline operations such as `BPUSH`.

---

## 41. Bag introspection

### ACTIVE

```jx
$q = bag.quotient();
$capacity = bag.capacity();
$used = bag.used();
$id = bag.id();
```

Interpretation:

```text
capacity  total underwritten capacity
used      accounted state usage
quotient  remaining capacity / oversight value
id        compact Bag identity
```

Do not treat `id()` as a raw memory address.

---

## 42. Bag source bindings

### PHP-BACKED / documented v0.1 contract

A Bag may own a serializable descriptor saying where data should come from:

```text
source
 -> through named query/listener
 -> at Bag node
 -> mode
 -> with options
```

Important separation:

```text
Bag binding = relationship metadata
live SQL/socket/client handle = host mechanism, never serialized into the Bag
```

Binding descriptors may contain safe information such as:

- source name,
- query/listener name,
- destination node,
- mode,
- coercion,
- safe parameters,
- revision/scope metadata.

They must not contain passwords, private keys, live PDO handles, live sockets, or secret TLS material.

---

## 43. Binding coercion

### PHP-BACKED / documented active vocabulary

```text
raw
string
algebra
number
integer
float
boolean
json
```

A binding can shape incoming data before the value enters the Bag through the normal mutation boundary.

A binding does not bypass Bag ownership merely because the source is trusted.

# Part VIII — Bag-backed containers

## 44. Container principle

### ACTIVE PHP-backed runtime + hot-op lowering contracts

JX containers are Bag disciplines, not a second memory universe.

```text
Bag
|- record
|- vector
|- stack
|- queue
|- deque
|- map
`- set
```

Rule:

> **Be native while working; become canonical at the Bag boundary.**

---

## 45. Record

### PHP-BACKED

A record gives named fixed fields and allows the compiler/native shadow to use fixed offsets when possible.

```php
$state = jx\BagContainers::record(4096, [
    'health' => 'int',
    'phi' => ['type' => 'int', 'default' => 0],
]);
$state->put('health', 100);
```

Use a record for known structured state whose field names are semantically stable.

---

## 46. Vector

### PHP-BACKED

Contiguous indexed storage.

Good for:

- dense arrays,
- numeric sequences,
- prepared indexed iteration,
- cache-friendly hot working sets.

---

## 47. Stack

### PHP-BACKED

LIFO discipline.

Conceptual operations:

```text
push
pop
peek
```

Canonical Bag hot operations include push/pop forms that can lower very tightly when the element width/layout is fixed.

---

## 48. Queue

### PHP-BACKED

FIFO discipline, designed around a power-of-two ring where appropriate.

```php
$jobs = jx\BagContainers::queue(65536, 'Task');
$jobs->enqueue($task);
```

Good for jobs, events, channels, and ordered work.

---

## 49. Deque

### PHP-BACKED

Double-ended queue.

Supports front/back insertion/removal without forcing a general list representation.

---

## 50. Map

### PHP-BACKED

Hash-backed key/value discipline.

The native direction uses target-native hashing/probing rather than serializing every lookup through a generic Bag tree operation.

---

## 51. Set

### PHP-BACKED

Unique-key collection, generally hash-backed in the native strategy.

---

## 52. Canonical Bag hot operations

### ACTIVE contract

```text
BPUSH
BPOP
BPUSHF
BPUSHB
BPOPF
BPOPB
BEMPLACE
BPEEK
BRESERVE
BDIRTY
BSYNC
```

Aliases should collapse into these identities before execution.

`BEMPLACE` expresses insertion/emplacement without forcing every discipline to use the same physical algorithm.

# Part IX — Book, Page, Task, Binding, Delivery

## 53. Book

### ACTIVE / PHP-BACKED runtime

A Book is a coherent application/compiled unit.

Current JX surface recognizes:

```jx
book = Book.open("my-book");
```

An optional capacity may be supplied by the current engine.

A native compiled Book becomes `.64B`.

A Book may own/register Bags and Pages and ultimately package executable sections, manifests, schemas, assets, and generations.

---

## 54. `.64B`

### ACTIVE compiled package contract

`.64B` is a deterministic compiled 64-bit Book container.

Important rule:

> **The bytes identify the Book, not the filename extension.**

A renamed `.64B` should remain recognizable by its internal header/magic.

Native runtime dependencies should be compiled sections, not PHP source files.

---

## 55. Page

### PHP-BACKED / host-neutral UI concept

A Page is a runnable/visible surface backed by JX state.

Conceptual Page model:

```text
Page
|- Controls
|- Bags
|- Collectors
|- Layout
|- Style
|- Events
`- PASL/JXL reactions
```

A browser may render a Page as HTML/CSS. Win32/X11/JX11 hosts may render native/composited surfaces. HTML is an output, not the definition of the Page.

---

## 56. Task

### ACTIVE JX surface / PHP-BACKED runtime

Current surface form:

```jx
task = Task.underwrite(4096, "worker");
```

Task is an execution Bag with identity and state.

Native/OSAura task scheduling is a mechanism. JX task meaning should remain host-neutral.

---

## 57. Binding

### PHP-BACKED semantic type

Page Binding means:

```text
Page -> uses Bag
```

It is intentionally different from a Bag's external-source binding.

This separation allows a Page to consume the same Bag regardless of whether that Bag was fed by SQL, NoSQL, a channel, local computation, or a future source.

---

## 58. Delivery

### ACTIVE JX surface

Deep extraction:

```jx
$value = delivery(root, "a.b.c");
```

Alias:

```text
deliver(...) -> delivery(...)
```

An optional default is supported by the JX engine shape.

Delivery exists so structured path access has one semantic operation rather than repeated ad-hoc host array/object probing.

---

# Part X — Controls, style, and UI state

## 59. Control

### PHP-BACKED host-neutral contract

A Control describes what exists on a Page.

The current architectural law is:

> **A control is a Bag-backed identity. A window is its placement. A source is its current dependency.**

Moving a Control/view must not destroy its data identity.

---

## 60. Borrowed views

### Runtime architecture / JXL direction

Rendering should borrow a stable Bag/view reference rather than copy the full control state every time.

```text
Control Bag
    |
    +--> View A
    +--> View B
    `--> mirrored view
```

Moving View B changes placement only.

Rule:

> **Clone the view, borrow the Bag, copy only on semantic mutation.**

A semantic mutation advances the Bag generation.

---

JX intentionally uses familiar CSS-like property names:

```text

background
background-color
background-image
background-opacity
background-size
background-position
background-repeat
image-opacity
border
border-width
border-radius
font-size
font-weight
width
height
min-width
min-height
max-width
max-height
margin
padding
gap
row-gap
column-gap
opacity
```

The property vocabulary is the contract. CSS is merely one renderer.

---

## 62. Hex colors

### PHP-BACKED style contract

```text
#RRGGBB
#RRGGBBAA
```

A Bag may hold colors when they are theme/live state.

---

## 63. Opacity distinctions

### PHP-BACKED style contract

```text
background-opacity = background image only
image-opacity      = foreground image content
opacity            = final composed control
```

Intrinsic source-image alpha should multiply with JX opacity, not be discarded.

# Part XV — Concurrency, jobs, events, and the processor bus

## 81. Program attention

JX's runtime direction aligns visual and processor attention.

```text
top/focused window
 -> primary listener PID
 -> processor bus route[0]
 -> remaining programs by PID
```

The top program is listened to first, while background ordering remains deterministic.

---

## 82. Processor-owned multiplex bus

### Runtime architecture

The bus does not copy entire Bags.

It carries a compact change descriptor:

```text
Bag ID
Bag generation
change kind
borrowed stable reference/pointer when needed
source PID
flags
```

Conceptual traversal:

```text
Bag generation changes
 -> processor buffer publishes borrowed reference
 -> CHECK: preferred listener / foreground, then PID order
 -> programs inspect and acknowledge
 -> processor deals result
 -> RETURN through same route
```

Memory owns Bags. The processor holds hot references/descriptors.

---

## 83. Sleeping and waking

A bus wake should not steal unrelated scheduler state.

If a program was already awake, acknowledging a bus event should not put it to sleep.

If the bus woke a sleeping program solely for inspection, it may restore that program to sleep after acknowledgement.

This principle prevents “attention” from becoming scheduler corruption.

# Part XVI — JX11, browser, Win32, X11

## 84. Host-neutral rendering

JX state should survive host changes.

```text
Book / Page / Bag / Control meaning
           |
           +--> browser
           +--> Win32 / WSJX64
           +--> X11/JX11
           `--> future host
```

The host supplies mechanisms. JX owns meaning.

---

## 85. Dirty rendering

A renderer should redraw changed regions rather than blindly repaint the entire display.

The current JX11/Osaura direction aggregates damage rectangles and prepares visible z-order once per compose instead of sorting surfaces inside every pixel.

Again:

> **Prepare structural work once; keep the repeated pixel path small.**

# Part XVII — JXL: the prepared language beneath the language

## 86. JXL is not source syntax

### JXL

The new JXL byte rule is:

```text
0xxxxxxx = executable JXL opcode
1xxxxxxx = attached extension/data; never opcode
```

This is intentionally distinct from global JX Hot-Call ABI v4:

```text
1xxxxxxx                  = one-byte HOT call
0xxxxxxx xxxxxxxx         = two-byte EXTENDED call
```

A Book chooses/binds its decoder mode at admission. The hot executor should not branch on mode for every instruction.

See `docs/JXL-PREPARED-EXECUTION.md`.

---

## 87. JXL register windows

### JXL

JXL can expose up to 256 logical register identities through compiler-prepared blocks with eight locally hot register selectors.

```text
32 windows * 8 register IDs = 256 logical IDs
```

A window is prepared metadata, not a programmer-written page-switch command.

---

## 88. JXL and the eight-shadow rule

The global JX/OSAura Hot-Call ABI retains exactly eight shadows per hot bank.

JXL can invoke prelinked targets that ultimately map to those services, but the JXL byte decoder must not confuse attached high-bit bytes with ABI-v4 high-bit hot opcodes.

The separation avoids ambiguity while preserving prepared eight-way working sets.

---

# Part XVIII — The global Hot-Call ABI v4

## 89. HOT call

### Runtime ABI

```text
1bbbbsss
```

where:

```text
bbbb = bank 0..15
sss  = shadow 0..7
```

Therefore:

```text
16 banks * 8 shadows = 128 one-byte hot entries
```

Each high-bit opcode is complete in one byte.

---

## 90. EXTENDED call

### Runtime ABI

```text
0fffffff ssssssss
```

Exactly two bytes.

```text
family = first byte & 0x7F
slot   = second byte
```

The first-byte MSB alone decides instruction length.

---

## 91. Protected F0-FF

### Project invariant

The fixed global subsystem map currently treats:

```text
F0-FF
```

as protected/unassigned.

Do not consume those slots casually. Any future assignment requires explicit ABI ratification.

# Part XXIV — The coming flood of information

## 120. Why JX needs strong boundaries now

JX is no longer only a parser experiment. The product surface now touches:

- language syntax,
- PASL algebra/control flow,
- Bags and containers,
- Books and deterministic packaging,
- JXL,
- native ELF/PE output,
- OSAura64,
- WSJX64,
- JX11,
- task scheduling,
- processor buses,
- hot call banks/shadows,
- SQL/NoSQL,
- browser hosting,
- media and chart plugins,
- live patching/generations,
- security/capability boundaries,
- AI-authored source and documentation.

That volume will continue to grow.

The answer must not be to pour every new fact into one mutable runtime dictionary.

The product should absorb information in layers:

```text
CANONICAL SOURCE
what humans and AI mean

SEMANTIC MODEL
what the compiler proves

BOOK / BAG MODEL
what must persist

JXL / NATIVE PREPARATION
what execution can remember once

REGISTER / HOT TABLES
what must react immediately

PROCESSOR / KERNEL MECHANISMS
what executes and moves data
```

This lets the system grow without making the repeated path proportional to the total amount of information in the product.

---

## 121. The information-weight rule

As JX gains thousands of methods, schemas, controls, source bindings, plugins, operations, and compiled generations, hot execution should not become slower merely because the catalog is larger.

The compiler/prelinker should turn large semantic catalogs into small prepared working sets.

```text
large Book knowledge
       |
       | compile / bind
       v
small hot working set
       |
       v
8-shadow banks / register windows / prepared routes
```

The weight belongs in preparation and storage, not in repeated lookup.

---

## 122. AI and JX

AI-generated JX should be held to the same canonicality rule as human-written JX.

AI should prefer:

- explicit meaningful names,
- standard canonical operations,
- documented aliases only,
- Bag ownership for persistent state,
- clear loop/branch structure,
- status-aware use of ACTIVE versus PLANNED syntax,
- no manual bytecode tricks in application source,
- no invented host-specific semantics.

The compiler can then optimize AI-generated source just as it optimizes human source.

A huge future corpus of JX source is an argument **for** canonical readability, not against it.

# Part XXV — The engine and the language

## 123. What PHP does

PHP is currently the clearest front-end engine for JX because it can:

```text
read canonical source
normalize aliases
manage compiler objects
execute the present Bag/Book/Task runtime
host web/server applications
shape SQL/NoSQL data
build deterministic packages
produce diagnostics
invoke PASL/PASM compilation
prepare native/JXL artifacts
```

This gives JX a practical development environment today while the native execution path becomes increasingly complete.

---

## 124. What PASL/PASM does

PASL is the lowerable arithmetic/control-flow language layer. PASM is the execution/assembly engine beneath it.

Current compiled PASL includes important forms such as:

```text
integer assignment/algebra
increment/decrement
compound arithmetic/bitwise mutation
while
for
if/else
select/switch
break
continue
complex values/arithmetic
```

JX can delegate pure lowerable fragments to this compiler/VM/native path.

---

## 125. What JXL does

JXL is where more of the compiler's decisions can become persistent prepared execution.

It carries compact executable operations and attached data under the new byte law:

```text
0xxxxxxx executable
1xxxxxxx attached data
```

It can bind blocks to eight-register windows over a 256-register logical file, retain prepared branch/operation identities, and live inside `.64B` Books.

JXL is the bridge between readable JX and repeated native-like execution.

---

## 126. What `.64B` does

`.64B` is the product artifact: a deterministic compiled Book that can carry the semantic state and executable sections needed by a native runtime.

The long-term deployment story is therefore straightforward:

```text
write JX
compile with the PHP-backed front end
emit a compiled Book
run the Book without requiring the original PHP source
```

# Part XXVII — Final orientation

JX is best understood as three cooperating products:

```text
1. JX
   the readable user-facing language and semantic model

2. PHP-backed JX front end
   the practical compiler/tooling/web host that understands and prepares JX

3. JXL / native execution
   the compact prepared form that avoids doing canonical work repeatedly
```

Around them are the durable systems that let the language scale:

```text
Bags      remember structured state
Books     package applications and generations
Pages     describe visible/runnable surfaces
Tasks     own execution state
Bindings  connect Pages/Bags/data sources without leaking mechanisms
JX11      presents host-neutral UI meaning
OSAura    supplies kernel mechanisms
WSJX64    supplies a native Windows-hosted machine
```

The language should remain recognizable to a PHP programmer without being imprisoned by PHP runtime costs.

The compiler should become increasingly capable without forcing compiler complexity into ordinary source.

The runtime should remain fast as the product's information inventory grows by preparing small working sets from large semantic Books.

And JXL should carry the decisions that programmers should not have to repeat manually.

> **JX is the clear language people and AI write. PHP is the powerful front end that helps understand and build it. JXL is the prepared execution the compiler remembers. Bags preserve meaning. Registers and hot shadows react. `.64B` carries the finished Book into the machine.**

That is the direction of the language as the amount of information, code, UI, data, devices, plugins, and native execution behind JX continues to expand.
